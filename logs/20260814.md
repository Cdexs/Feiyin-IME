### 切换前先纠正了一个长期假象

`collab/todo.md` 与 pane 编辑框脚注长期显示 coder-1 = `glm-5.2 Ollama Cloud`、
coder-2 = `kimi-k2.7-code Ollama Cloud`，但**实际一次请求都没走过这两个模型**。

取证（`~/.local/share/opencode/log/`，`directory=D:\Workspace\CodeLab\voice-ime`）：

**结论**：OpenCode 编辑框脚注 `┃ Build · <model>` 不可作为「当前实跑模型」的判据，
唯一权威判据是 `~/.local/share/opencode/log/*.log` 的 `modelID=`（配合 `directory=` 定位是哪个项目）。
消息体上方的 `▣ Build · <model> · <耗时>` 才是产出该条消息的真实模型。

### 切换方式：必须重启，禁止 TUI 内切

`configs/team-voiceime.yaml` 内有明令：🔴「不要在 OpenCode TUI 里手动切换模型——切换会导致
Worker 卡死」（Gavin 2026-08-03 实测，`troubleshooting.md [WORKER-HANG-001]` 补充三）。
配套 `todo.md` 2026-08-04 记录：`opencode -s <session> -m <model>` 恢复会话时 `-m` **静默不生效**。

执行：`source replace-worker.sh && replace-worker <id> OpenCode <provider/model>`
（该脚本第 3 参数可显式指定模型，会拼成 `opencode -m <provider/model>` 全新启动）。

**验证**：重启后新日志 `055558.log` → `modelID=glm-5.2`（coder-1）、
`055547.log` → `modelID=kimi-k2.7-code`（coder-2）。切换生效。

**代价**：两个 Worker 会话上下文清零（coder-1 99.7K/50%、coder-2 33.2K/17%）。
因当时三 Worker 全空闲、outbox 全 0 字节、工作区 `src/` 干净、无在途任务，代价仅为重读协作文档。

## 2026-08-14 — 修复 Worker 重启上下文注入静默丢失 + 启动模型默认值落库（Gavin 指令）

**Gavin 指令**：「注入的缺失缺陷要修，而且你要把启动初始化脚本里面，把 coder1 和 coder2 的模型
修改为现在设置的模型，接下来每趟启动都默认使用这个模型来启动。」

### 一、启动模型默认值

**结论：改 yaml 即可，无需改 init-collab.sh。** 取证：`init-collab.sh:336` 调用
`build_worker_cmd`（`lib/config-parser.sh:329`），后者读 yaml 的 `model:` 字段拼 `-m <provider/model>`
—— **yaml 是启动模型的唯一权威源**，`init-collab.sh` 全文零处硬编码模型。

`collab/configs/team-voiceime.yaml` 现值：

| Worker | model |
| --- | --- |
| coder-1 | `ollama-cloud/glm-5.2` |
| coder-2 | `ollama-cloud/kimi-k2.7-code` |
| tester-1 | `opencode/deepseek-v4-flash-free`（未动） |

`state.json` 的 `config_file` 指向该 yaml；`configs/default.yaml` 是 `worker-1/worker-2` 通用模板，
与 voice-ime 无关，不冲突。

### 二、注入丢失缺陷修复

**根因两层**：① 就绪判据 `Build|Ollama|kimi|glm|ctrl\+p|esc interrupt` 在 OpenCode 启动横幅
阶段即命中，早于输入框挂载 → 注入被终端吞掉；② 注入后零校验且带 `|| true`，
「发出去」被当成「送到了」，故障完全静默。

**修复**：① 三处判据统一改为只认输入框占位符 `Ask anything`；
② 注入改为「打字校验（占位符应消失）+ 提交校验（`esc interrupt` 或占位符回归）」双段回读，
各最多 3 次；③ 三次全败则明确报错并写 `comms.log` 标 `[CONTEXT_INJECT_FAIL]`，不再谎称成功。

**改动文件**：`collab/replace-worker.sh`（判据 1 处 + 注入块）、
`collab/init-collab.sh`（判据 2 处 + 注入块 1 处）。两者 `bash -n` 语法验证通过，旧判据零残留。

**残余风险已写明**：判据依赖 OpenCode 占位符字面量，上游改文案会使就绪检测失效并走满 30s 超时，
但第二层回读校验仍生效，不会退化为静默丢失。详见 `troubleshooting.md [REPLACE-WORKER-INJECT-LOST-001]`。

## 2026-08-14 — TEST-PROMPT-AB-033 派发 + 7.3 修订（保真度门禁逼出阶段六不保真事实）

**派发**：`ADD_PUNCT` 单变量 A/B，三组 24 次调用，模型锁死 `deepseek-v4-pro`。

**主控任务书缺陷两处，已下发 7.3 修订版**：
① 假定「快照 = 今天的提示词」—— 该假定对源码常量成立（git 比对已证），对快照 JSON 不成立；
② **完全没写组装顺序** —— 而 `harness_025f.py` 把 `WORDBOOK` 排在 `SUGGESTION` 之后，
与生产层序（`src/llm/mod.rs:356-443`）不符，这比长度偏差更影响结论。

**附带查出的重要事实**：阶段六实验**本身就不是生产保真的**（无场景块、无 extra、层序不同、

对生产未必成立 —— 这解释了「实验说解决了、生产仍出问题」的表面矛盾。详见
`troubleshooting.md [F3-UNORDERED-LIST-001]` 第十节。

**G0 明确不套保真度门禁**：其参照系是「那次实验」而非「今天生产」，
