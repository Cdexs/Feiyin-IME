## 2026-07-25 — WORDBOOK-AUTOLEARN-FIX-001-TAURI：Tauri 侧默认 prompt 词库建议段改为单词模式

**改动文件**：`src-tauri/src/i18n.rs`

**改动原因**：Gavin 报告 LLM 自动添加系统词库词条不生效。主控诊断发现默认 system_prompt 的 Wordbook Suggestions 段仍是 DEC-029 之前的词对格式（`{"suggestions":[{"raw":"...","corrected":"..."}]}`），而词库已改为单词模式（DEC-029），故需统一为单词格式。

> **主控验收纠正（2026-07-25）**：coder-2 原文此处写「运行时解析只认字符串数组，导致建议入库失败」——**该因果表述不成立**。`parse_suggestion_line`（src/llm/mod.rs:1042）先试 `StringEnvelope`（裸字符串数组），失败再回退 `SuggestionEnvelope`（`{raw, corrected}` 词对，取 corrected 侧），**两种格式都能正确解析**，旧格式从未导致解析或入库失败。
>
> 本项（方向 D）的真实价值是**消除格式口径不一致**（默认 prompt 说词对、运行时追加指令说单词数组，同一个 prompt 内两套格式并存会降低 LLM 遵循度），而**不是**修复一个解析 bug。真正导致"不生效"的是另外两项：A（用户 config 的 `strictly prohibited: adding suggestions` 条款与 SUGGESTION_INSTRUCTION 正面冲突 → 触发率仅 13.5%）与 C（返回 ASR 错字侧 + 零过滤）。完整诊断见 troubleshooting [WORDBOOK-AUTOLEARN-001]。
>
> 记录此纠正的原因：若留下"D 修了解析 bug"的错误因果，未来若机制仍不生效，排查者会误以为格式问题已解决而不再怀疑 prompt 冲突，重走弯路。

**具体改动**：
1. 在 `default_system_prompt_en` 的 ZH、ZH_TW、EN 三处副本中，把第 7 条 Wordbook Suggestions 段从词对格式改为单词格式：
   - JSON 结构：`{"suggestions":["correct_word"]}`
   - 措辞改为强调"检测到应学入词库的单词"，并明确收录范围：专有名词、品牌名、人名、技术术语、专业词汇、日常生活词汇、常用语、成语
   - 新增约束：只返回纠正后的正确写法，且该词必须出现在 `<corrected>` 文本中（`verbatim`），禁止返回被改掉的错误写法
2. 与 coder-1 主程序侧（`src/i18n.rs` 三段 + `src/llm/mod.rs` 运行时追加指令）措辞对齐，两侧最终口径一致。

**影响范围**：仅 Tauri 设置 UI 的默认 system_prompt；不改变 UI 字符串、不改版本号、不改任何 Rust 业务逻辑。

## 2026-07-25 — WORDBOOK-SCHEMA-FIX-001-CORE：词库 schema 三态条件化 + 残留临时表救援 + busy_timeout + 日志提升（P0 修复）

**Task 1 三态条件化 init_schema**：用 pragma_table_info + sqlite_master 双查判定库状态：
- **A 全新库**（wordbook 表不存在）→ 直接建 word 模式 schema（新增 const WORD_SCHEMA，不复用 003 的 wordbook_new 临时表定义，避免两处漂移）
- **B 旧库**（有 raw 列）→ 完整迁移链 001→002→import_legacy_words→normalize_source→003→finalize→normalize_source
- **C 已迁移**（有 word 列，无 raw 列）→ 完全跳过 001/002/legacy import，只做幂等保障（确保 idx_wordbook_new_unique 索引存在、确保 wordbook_candidates(word) 表存在、normalize_source 先 SELECT 判断有非法值才 UPDATE 避免写放大）

索引名保持 idx_wordbook_new_unique 不变（003 迁移历史产物，现存库就叫这个名字）。

**主控修法一：残留临时表救援**：finalize 的四步 DROP+RENAME 原无事务，若进程在「DROP wordbook 之后 RENAME wordbook_new 之前」被杀，库状态是 wordbook 表不存在而 wordbook_new holding 唯一数据副本。初版"一律 DROP 残留临时表"会销毁唯一副本 → 判为状态 A 建空 schema → 用户词库静默清空不可恢复。新增 `recover_stale_temp_tables`：清理前先判断真表是否存在，真表不存在而 _new 存在 → ALTER TABLE _new RENAME TO 真表 救回数据（log::warn! 标记），真表存在而 _new 存在 → _new 是半成品副本安全 DROP。wordbook/candidates 两侧独立判断。

**主控修法二：finalize DROP+RENAME 事务包裹**：四步改用 `conn.unchecked_transaction()` 包成原子单元，若中途崩溃会回滚，「旧表已删、新表未改名」中间态从此不可能持久化到磁盘。
