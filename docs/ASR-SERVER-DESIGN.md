# 本地实时识别对外服务 —— 方案（草案，待 Gavin 拍板）

> 单号：`ASR-SERVER-491`（设计阶段，未动代码）　日期：2026-10-17
> 需求原话（Gavin）：「将本地的实时的流式服务扩展成一个本地的流式asr 语音服务，这样可以支持局域网/广域网（通过网络地址）内的其他电脑端的输入法客户端通过 web socket 的协议，或者安卓端/ios 端语音输入法通过协议……来调用」
> 约束原话：「不要在系统的性能、资源占用，还有对现在的架构不会产生破坏性的影响的前提之下，考虑方案」
> 结构建议原话：「把目前的这个本地实时流式的语音服务作为一个核心的服务，另外再增加1层这个服务进程，这个服务专门提供 web socket 和 aoq 的对外的协议连接服务的接口，然后这个服务的进程和我们内核的这个进程之间，通过进程ipc来进行调用」「不会对现有的这个输入法的内核服务产生破坏性的影响。当然，你要仔细考虑是否有更优的方案」
> 启用方式原话：「最终的这个本地流式 asr 语音服务启动的时候，用户可以选择是否启动协议服务进程。如果启动的话，那不光本地语音输入法可以直接用，也可以局网内，或者说外网的其他的电脑终端和 app 端也可以调用」

---

## 0. 结论先说

1. **采用 Gavin 的「内核 + 对外服务进程 + IPC」结构**，只做一处细化：**内核就是现在的输入法进程 `feiyin-ime.exe`**，不另起内核进程。模型只有一份，本机输入法的路径不多一跳。
2. 新增一个独立程序 **`feiyin-asr-gateway.exe`**（下称「网关」），负责所有对外的事：WebSocket、QUIC、鉴权、断线续传、音频解码、并发限流。它**不加载任何模型**。
3. **默认关闭**。关闭时网关不启动、不监听端口、内核里不多占一个线程，行为跟现在逐位相同。
4. **阿里的 AOQ 兼容不了，但可以对标**：AOQ 是阿里私有的 QUIC 传输，只能通过阿里的 Android/iOS/鸿蒙 SDK 连阿里云，没有公开规范。我们在网关里自建 **QUIC 通道**，消息格式跟 WebSocket 版完全相同，能拿到 AOQ 的主要好处：Wi-Fi 和 4G 切换不断线、丢包不卡后续音频、重连快。
5. **对外协议对齐阿里的 DashScope `run-task` 协议**：阿里给输入法推荐的 `qwen-audio-3.1-asr-flash-message` 用的就是它，**我们自己的在线识别客户端也已经在说这套协议**（`src/transcription/qwen_inference.rs:263` `build_run_task_message`）。好处是另一台电脑上的飞音只要把在线识别地址改成局域网地址就能用，客户端几乎不用写新代码。
6. **本机优先**：本机正在说话时，远程会话的精解（1.7B）排队让路。上限是远程最多同时 2 路，超出的连接直接回「忙」。

## 2. 为什么选这个结构（三种做法对比）

| 做法 | 资源 | 对现有架构 | 稳定 / 安全 | 结论 |
| --- | --- | --- | --- | --- |
| A. 服务直接写进输入法进程 | 最省 | 网络依赖进主程序 | 外网来的数据在输入法进程里解析，出问题会**连带输入法崩溃** | ✗ |
| B. 另起一个「内核进程」装模型，输入法也改成通过 IPC 调它 | 模型一份 | **输入法本机路径要整个改造**，多一跳 | 好 | ✗ 破坏面太大 |
| **C. 输入法进程当内核 + 独立网关进程（Gavin 方案）** | 模型一份；网关约十几 MB 内存 | 本机路径不变，内核只多一个 IPC 入口 | 外部数据只在网关里解析；网关崩了自动重启，**输入法不受影响** | ✅ **推荐** |

还考虑过 **D.「内核一行不改」**：远程会话直接排进现在的 worker 线程。代价是 worker 一次只能跑一个会话：远程有人在说话时，本机按热键要么干等，要么把远程掐断，**本机体验反而受损**。所以不选。C 方案对内核唯一的改动见 §4：把本地实时会话那 1700 行**原样搬进独立函数、加参数**，用回放录音保证本机结果逐位不变。这是「内核不被破坏」能做到的最小改动。

C 方案的额外好处：
- 网络相关依赖（QUIC、Opus 解码、TLS 服务端）**只进网关**，主程序体积和依赖不变；
- 网关可以单独重启、单独升级；
- 网关跑在普通用户权限下，攻击面被关在它自己的进程里。

## 3. 整体结构

```
 其他电脑上的飞音 ─┐                       ┌──────────── feiyin-ime.exe（内核，现有进程）────────────┐
 安卓 / iOS 输入法 ─┼─ WebSocket ─┐         │                                                         │
 第三方程序 ───────┘   QUIC ─────┤         │  IPC 服务（新增，一个线程）                              │
                                 ▼         │     │                                                   │
                      feiyin-asr-gateway.exe│     ▼                                                   │
                      · 鉴权 / 限流         │  会话引擎（从 worker 抽出来的本地实时会话，§4）           │
                      · Opus → PCM          │     │  本机录音会话 ──┐                                │
                      · 断线续传缓存        │     │  远程会话 1..2 ─┼─→ 同一份模型（1.7B / 对齐 / 预览）│
                      · 协议翻译            │     ▼                 │                                │
                      · 心跳 / 发现         │  结果 → IPC 回网关     └─ 本机优先调度                   │
                              ▲  命名管道 / Unix socket（仅本机、仅当前用户）                          │
                              └────────────┴─────────────────────────────────────────────────────────┘
```

- **IPC**：Windows 用命名管道 `\\.\pipe\FeiyinIME.AsrCore`，macOS 用 Unix socket，权限只开给当前用户。帧格式是「长度 + 类型 + 内容」，只有 6 种：
  - 网关发给内核：开会话（参数）、音频（16k PCM）、结束、取消
  - 内核发给网关：结果（预览 / 定稿）、出错 / 结束
  - 每路音频 32KB/s，本机管道延迟远低于 1ms，可以忽略。
- **生命周期**：设置里打开开关 ⇒ 内核拉起网关（跟 crash-reporter 同一种拉起方式）。网关意外退出，内核在 5s 后自动重拉。关掉开关或退出输入法，网关一起结束（Windows 用 Job 对象保证不留孤儿进程）。

## 4. 内核里唯一的结构改动：把「本地实时会话」抽成可复用函数

**现状**：会话逻辑内联在 `spawn_worker_thread` 里，而且 worker 线程一次只跑一个会话。如果远程会话也走 worker，本机按热键就要等远程说完，不可接受。

**改法**：把 `main.rs` 约 8940–10700 行原样搬进新模块 `src/transcription/localrt_session.rs`，参数化成：

```rust
pub fn run_session(
    audio_rx: Receiver<Vec<f32>>,   // 本机 = 麦克风；远程 = IPC
    engines: &LocalRtEngines,        // 共享的那一份模型
    opts: SessionOpts,               // 本机 / 远程差异（见下表）
    sink: &mut dyn SessionSink,      // 本机 = 发 PipelineEvent 给浮层；远程 = 发 IPC 帧
    cancel: &AtomicBool,
) -> Result<SessionOutput>
```

- 本机路径：worker 调 `run_session(麦克风, …, 本机选项, 浮层 sink)`，**行为必须逐位不变**。
- 本机与远程的差异只放在 `SessionOpts` 里：

| 项 | 本机 | 远程 | 原因 |
| --- | --- | --- | --- |
| 声纹剔除（DEC-089/099） | 照旧 | **关** | 声纹是本机主人的，远程用户是别人 |
| 近场门 / 跨录音音量沿用（389） | 照旧 | **关** | 按本机麦克风标定，远程设备不适用 |
| 自动学习词库 / 声纹注册 / 使用统计 | 照旧 | **不写** | 远程数据不得污染本机主人的学习数据 |
| 词库注入 | 照旧 | 本机词库 + 客户端 `vocabulary` 追加 | 跟阿里协议的 vocabulary 字段对齐 |
| 预览线程数 | 物理核数（DEC-100） | **2** | 不跟本机抢 CPU |
| 后处理 / 上屏 | 照旧 | 不做 | 见 §5.3 |

- **进程级共享状态要拆成按会话的**：`localrt_vad_session` 的 VAD 缓存（`local_stream.rs:1446`）、`LOCALRT_CARRY_LEVEL` 等现在是进程级单份。远程会话各自建一份 VAD（模型很小）；本机继续用现在的缓存，不变。
- **验收护栏**：抽取前后，用现有回放录音（`replay436_tests.rs` 等）跑本机路径，**事件序列 + 终稿文字逐位相同**。这是「不破坏现有架构」的硬证据。

### 本机优先调度

- 1.7B 精解和对齐的锁外面加一层「本机优先闸」：本机会话在等锁时，远程任务不许插队。
- 远程某一窗已经开始解了，不会被打断。但本机开口后第一次派发至少要等 1.2s 静默或说满 10s（DEC-088），通常那一窗早已解完。**最坏情况本机多等一窗的解码时间，PoC 里实测给出数字**（§7）。
- 本机正在录音时，远程预览的重解间隔从 0.6s 放宽到 1.2s。

## 5. 对外协议

### 5.1 主协议：DashScope `run-task`（WebSocket，PCM 或 Opus 二进制帧）

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| 客户端 → | `run-task` | `parameters.format` = `pcm` / `opus`，`sample_rate` = 16000，可带 `vocabulary`；鉴权放在 `Authorization: Bearer <访问码>` |
| 客户端 → | 二进制音频帧 | 建议 100ms 一帧 |
| 客户端 → | `finish-task` | 说完了 |
| ← 服务端 | `task-started` | 可以开始发音频 |
| ← 服务端 | `result-generated`，`sentence_end=false` | **预览**（SenseVoice 模拟流式），同一 `sentence_id` 会反复更新 |
| ← 服务端 | `result-generated`，`sentence_end=true` | **定稿**（1.7B 精解 + 对齐拼接后），带 `words` 逐字时间 |
| ← 服务端 | `task-finished` / `task-failed` | 结束 / 出错 |

**句子怎么切**：一个派发片对应一个 `sentence_id`。定稿时机就是本机浮层里这段文字「不再被改写」的那一刻（DEC-100 冻结点，加上 DEC-095 对齐晚到后的重拼完成），保证 `sentence_end=true` 之后绝不再改。

**扩展字段**一律放在 `payload.output.feiyin.*` 下，标准客户端会自动忽略：续传序号、本机忙闲提示等。

### 5.2 兼容协议（第二期）：千问实时识别风格

给已经接过 `qwen3-asr-flash-realtime` 的第三方程序用：`session.update` / `input_audio_buffer.append`（base64）/ `session.finish`，回 `conversation.item.input_audio_transcription.text` / `.completed`。在网关里做一层格式翻译，内核不感知。

### 5.3 后处理：按节点拆开，由调用端选（详见 §13）

> 🔴 10-17 修订：原稿写的是「服务端只回原文」，**这是错的**。我们的电脑客户端走在线识别时，**默认服务端已经做过数字规整，自己会跳过这一步**（`main.rs:16561`，V091-ITN-SKIP-ONLINE-215）。照原稿做，客户端会漏掉数字规整。改为按节点拆分、由调用端在请求里点选，见 §13。

## 6. 弱网对策（借鉴 AOQ 的思路，自己实现）

> 🔴 10-17 修订：下表「QUIC 通道」一行撤销，改用 WebRTC（开放标准，手机端现成），Opus / 心跳由 WebRTC 自带。见 §14.3。

| 手段 | 做在哪 | 效果 | 期数 |
| --- | --- | --- | --- |
| **Opus 压缩** | 客户端编码，网关解码 | 16k PCM 是 256kbps，Opus 语音约 20~24kbps，**流量降到约 1/10**，弱网下不容易堵 | 二 |
| **断线续传** | 网关 | 每帧音频带序号；断线后网关保留会话 15s；客户端带同一 `task_id` 重连时，网关回「已收到第 N 帧」，客户端从 N+1 补发，已发过的结果补推。**会话在内核里不中断**，用户感知只是停顿一下 | 二 |
| **心跳** | 网关 | 跟阿里一样发 `heartbeat=true` / `sentence_id=0` 的保活包，防止路由器 NAT 超时把连接掐掉 | 二 |
| **QUIC 通道（对标 AOQ）** | 网关（Rust `quinn`） | 走 UDP：Wi-Fi 和 4G 切换时连接迁移不断线；丢一个包不卡后面的音频；重连 0-RTT。消息格式跟 WebSocket 版完全相同 | 三 |
| 回声消除 / 降噪 | 手机客户端 | 用系统自带能力（Android `AcousticEchoCanceler` / iOS VoiceProcessingIO），服务端零成本 | 客户端 |

> 关于 QUIC 客户端：iOS 15+ 系统网络库原生支持 QUIC；Android 要带 Cronet 或 quiche 库；浏览器不支持裸 QUIC，所以浏览器场景只用 WebSocket。这也是阿里 AOQ 同样「不支持浏览器」的原因。

## 7. 资源与性能保证（对应 Gavin 的约束）

| 承诺 | 怎么保证 | 怎么验证 |
| --- | --- | --- |
| 关闭时零影响 | 开关关 ⇒ 不拉网关、不建 IPC 线程、不监听端口 | 进程列表 / 端口列表 / 内存对比；本机回放逐位相同 |
| 不多一份模型 | 远程会话共用内核里已加载的那一份；本机档位不是「本地实时」时（模型没加载）服务回「未就绪」，**不为远程单独加载模型** | 开启前后显存 / 内存对比 |
| 本机体验不变差 | 本机优先闸；远程预览 2 线程、本机录音时降频；远程最多 2 路 | **PoC 必测**：本机说话的同时回放 2 路远程录音，测本机每窗精解等待时间和预览刷新间隔，跟单独本机对比 |
| 网关自身 | 不加载模型，预计常驻十几 MB；空闲时不占 CPU | 实测 |
| 不破坏架构 | 本机路径只是「原样搬家 + 加参数」，有逐位护栏 | §4 护栏 |

## 8. 安全与外网

- **只用一个开关**（遵守 DEC-031 单开关原则）：「启动语音识别协议服务（允许其他电脑和手机调用本机识别）」。关闭时只有本机输入法自己用；打开后本机输入法照常直接用（不经网关），同时局域网 / 外网的电脑和 App 可以连进来。打开后自动生成访问码，显示在设置页，可一键复制、可重新生成。端口用固定默认值，不进配置界面。
- 没有访问码一律拒绝；同一 IP 连续输错 5 次锁 10 分钟；音频不落盘。
- **局域网**：第一期就支持。安装包给网关加防火墙规则，**只放行「专用网络」**，公共 Wi-Fi 下不开放。
- **外网**：第一期**不直接暴露公网**，推荐用 Tailscale / ZeroTier 这类组网工具把手机和电脑拉进同一个虚拟局域网，安全和穿透都由它解决。第三期再做内置 TLS 加公网地址，那时需要证书和域名，单独评估。
- 自动发现（第二期）：局域网里用 mDNS 广播 `_feiyin-asr._tcp`，客户端不用手填 IP。

## 12. 逐字时间戳：现在**不完全具备**，要补 6 处

### 12.1 现在有的

- 每个精解窗口出来后，0.6B 强制对齐器给**每个字的起止时间**：`llama_asr.rs:578` `AlignOut.char_times`，跟 `text.chars()` 一一对应。
- 对齐用的是**整窗原始音频**，不是剪掉静音后的音频（`main.rs:9218` 注释「用整窗音频（非剪静音后）⇒ 时间直接是窗内坐标」）。拼接器再加上窗口起点，换算成**整段录音的绝对秒**（`mod.rs:2920` `push_window_timed` 的 `times` 参数）。坐标系是对的，精度来自强制对齐，不是估算。

### 12.2 缺口（逐条对代码）

| # | 缺口 | 代码位置 | 后果 | 补法 | 影响本机吗 |
| --- | --- | --- | --- | --- | --- |
| T1 | **拼接器只留最后一窗的时间**，已定稿部分只存文字 | `mod.rs:2876` `committed: String`；`stitch()` 里 `self.committed.push_str(...)` 时，时间直接丢掉 | 整句的时间拿不全 | `OrderedReflow` 加一个与 `committed` 逐字对应的 `committed_times`，各拼接分支同步追加 | 不影响，只多维护一个数组；文字逐位不变（回放护栏） |
| T2 | **松键后最后一窗不做对齐**（DEC-095 ②，为本机省 0.25s） | `main.rs:9213` `if seq + 1 == final_windows… continue` | 最后一句没有时间 | **只对远程会话**照常对齐最后一窗 | 本机不变 |
| T3 | 两窗都没有时间时按比例估算接缝（371 兜底），或对齐结果不合格被丢弃 | `mod.rs` `stitch()` 的 `_ =>` 分支；`llama_asr.rs` `spans_valid` | 这段字没有时间 | 远程会话在该句定稿前对这段音频补对齐一次；补不出来的字标成「估算」 | 不影响 |
| T4 | 精解失败退回流式兜底文字 / 松键后整段兜底 | 406 兜底窗已对齐（DEC-098 ②）；整段兜底没有 | 极少数整段没有时间 | 远程会话对整段补对齐一次 | 不影响 |
| T5 | **预览**（未定稿文字）不往外传时间 | `local_stream.rs:1659` `state.on_result(sentence_id, &sim_hyp, false, &[])` 传的是空数组；SenseVoice 其实有逐 token 时间（`local_stream.rs:791` `r.timestamps`，只拿来找切点） | 预览文字没有时间 | 远程会话把 SenseVoice 的 token 时间带出去，**标成「粗略」**（CTC 时间，精度不如强制对齐） | 不影响 |
| T6 | **文字处理节点改了字，时间就对不上了**：接缝标点、同音纠错、数字规整（「二零二六」→「2026」）、标点模型插标点、去口水词、去句末标点 | 这些节点全是「进文字、出文字」，比如 `itn::normalize_numbers(&str) -> String`（`itn.rs:1241`），没有位置映射 | 处理后的文字没法回挂时间 | 见 12.3：不改节点本身，在外面套一层「前后对比，把时间搬过去」 | 不影响 |

### 12.3 T6 的做法：节点一个不改，外面套一层「时间搬运」

每个节点照旧「进文字、出文字」。服务端在外面套一层：把处理前后两段文字逐字对比，
- 没变的字：时间原样搬过去；
- 被替换的一串（「二零二六」→「2026」）：新的这串整体占用旧那串的起止时间；
- 新插入的标点：时间取前一个字的结束点（跟 `char_times_from_units` 里「标点取前一字时间」同一规则）；
- 删掉的字（口水词）：时间跟着消失。

这样节点内部不用改，以后新增节点也自动有时间。每个字额外带一个来源标记：`aligned`（强制对齐）、`estimated`（估算）、`rough`（预览粗略）。前端可以按标记决定怎么用。

### 12.4 对外格式

`result-generated` 的 `words` 按阿里格式给每字 `begin_time` / `end_time`（毫秒，相对本次会话第一帧音频）/ `text` / `punctuation`。来源标记放在扩展字段 `feiyin.ts_source`。**定稿句（`sentence_end=true`）里的每个字都保证有时间**，补不出的才标 `estimated`。

### 13.2 归属原则

- **必须在调用端**：要读调用端的窗口（场景、上屏）；要花调用端的钱（LLM）；属于调用端用户自己的数据（统计、词库学习、词库命中）。
- **必须在服务端**：要用模型和音频（识别、对齐、拼接）。
- **两边都行的纯文字节点**（2、3、6、7、8、9）：服务端做成**可选节点**，调用端按需点选。我们自己的电脑客户端本来就有这些代码，可以自己做；手机 App 没有，就交给服务端做。

### 13.3 松耦合的做法

1. **节点统一包一层接口**，节点内部一行不改：

   ```rust
   trait TextStage {
       fn id(&self) -> &'static str;            // "homophone" / "itn" / "units" / "punct" / "filler" / "l2"
       fn apply(&self, text: &str, p: &StageParams) -> String;   // 直接调用现有函数
   }
   ```

   外面再套 §12.3 的「时间搬运」，每个节点就自动带上时间。

2. **顺序由服务端固定，开关由调用端点**：节点之间有先后依赖（例如数字规整必须在 LLM 之前，DEC-036 双通道），所以调用端只能选「开 / 关」，不能改顺序。服务端始终按 13.1 的顺序执行。

3. **两种调用入口**：
   - **跟着识别一起做**：`run-task` 里带 `feiyin.postprocess: ["homophone","itn","units","punct","filler"]`，定稿结果同时给 `text`（识别原文）和 `feiyin.processed_text`（处理后），两份都带逐字时间。
   - **单独调用文字处理**：网关另开 `POST /v1/text/process`，请求是 `{text, words?, stages:[...]}`。**为什么必须有它**：LLM 在调用端，而它夹在数字规整（3）和标点 / 去口水词（7、8）之间。用 LLM 的调用端流程是：识别 + 节点 2、3 → 自己的 LLM → 再调一次文字处理做 6~9。

4. **兼容我们自己的电脑客户端**：客户端走在线识别时会跳过数字规整主通道（`main.rs:16561`），默认服务端做过了。所以客户端连我们的服务时请求 `postprocess: ["homophone","itn"]`，跟它对阿里服务的假设一致，客户端在这一点上不用改。

5. **本机输入法完全不走这层**：本机继续直接调用 `run_pipeline_core`，第一期不重构它。服务端的节点包装调用的是**同一批函数**。护栏测试：同一段输入，包装层输出必须与直接调用逐位相同，防止两边行为分叉。

## 14. 移动端协议：用开放标准，不自建（10-17 Gavin 问「有没有相关的开源协议可以用……自建成本比较高，你评估一下」）

### 14.1 「协议」其实分三层，贵的不在消息格式

| 层 | 内容 | 自建的代价 |
| --- | --- | --- |
| 消息格式 | 开会话、发音频、回预览 / 定稿 / 时间戳的 JSON | **便宜**：服务端几百行；但要自己写文档、测试工具，而且没有任何现成客户端 |
| 传输通道 | 断线重连、Wi-Fi/4G 切换、丢包、压缩、抖动 | **最贵**：QUIC 通道 + 续传要在服务端、安卓、iOS 三处各写一遍，还得在真实弱网里反复调。系统一升级（如 iOS 后台网络策略）就要跟着改 |
| 客户端 SDK | 手机端采音、编码、连服务、处理事件 | **很贵**：安卓、iOS 各一套，长期维护 |

自建一套协议，等于这三层全包；采用开放标准，我们只写**服务端适配层**，手机端直接用现成的库。

### 14.2 候选开放协议（已逐个核对原文）

| 协议 | 消息语义跟我们对不对得上 | 逐字时间 | 弱网 | 手机端现成支持 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **阿里 DashScope `run-task`** | ✅ `sentence_id` + `sentence_end` = 我们的「预览 / 定稿」 | ✅ `words[].begin_time/end_time` | 差（裸 WebSocket） | 官方 7 种语言示例；Java SDK 安卓可用 | **一期主协议**：我们的电脑客户端已经在用，零改动 |
| **OpenAI Realtime 转写**（`session.update` / `input_audio_buffer.append` / `conversation.item.input_audio_transcription.*`） | ✅ 能对上（预览走增量事件，定稿走 `.completed`） | ❌ 标准里没有，放扩展字段 | **有 WebRTC 版本**：同一套事件走 WebRTC 数据通道，音频走 Opus | 事实标准：阿里 `qwen3-asr-flash-realtime` 就是照它做的（官方示例连 `OpenAI-Beta: realtime=v1` 请求头都一样）；vLLM 等开源推理服务也实现了；各语言都有客户端库 | **二期移动端主协议**，WebRTC 版本解决弱网 |

| sherpa-onnx streaming server | 只有单遍流式，没有定稿概念 | 有 | 差 | 有安卓 / iOS 示例 App | ✗ 对不上两遍结构 |
| Wyoming（Home Assistant） | 面向智能音箱，没有逐步预览 | ✗ | TCP，差 | 无 | ✗ |
| 阿里 AOQ | — | — | 极好 | 只有阿里 SDK，连阿里云 | ✗ 私有，用不了 |
| IETF MoQ（Media over QUIC） | 媒体分发协议，不管识别语义 | — | 好 | 草案阶段，手机端库不成熟 | ✗ 太早 |

### 14.3 弱网怎么解决：用 WebRTC 替换原 §6 的「自建 QUIC」

WebRTC 是浏览器和手机通话的通用标准。安卓、iOS 都有谷歌维护的成熟实现，**AOQ 宣传的那几项它都有**：
- Opus 压缩和丢包补偿（FEC）；
- 抖动缓冲；
- 网络切换时 ICE 重启，Wi-Fi 换 4G 自动恢复；
- 回声消除和降噪内置。

OpenAI Realtime 本身就定义了 WebRTC 接入方式：客户端用 HTTP 交换一次 SDP，音频走 Opus，事件走数据通道。手机端用任何 WebRTC 库都能连，**这些弱网能力一行都不用我们写**。

#### 可直接调用的成熟开源库（10-17 Gavin：「有没有开源的比较成熟的这个协议库可以调用」）

| 方案 | 服务端库 | 手机端库 | 跨网络能力 | 我们要写的 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **LiveKit 全家桶**（开源，自部署） | LiveKit Server（Go 单文件，负责 WebRTC 转发 + **内置 TURN 中继**）+ 官方 Rust SDK `livekit` crate（基于 tokio；订阅用户的麦克风音轨，SDK 直接吐 PCM 帧，Opus 解码它做） | 官方 Android（Kotlin）/ iOS（Swift）/ Flutter / React Native SDK | **最强**：NAT 穿透、TURN 中继、网络切换自动重连（ICE 重启）、Opus FEC、抖动缓冲，全是现成的 | 网关里一个「识别代理」：作为房间成员收音轨 → IPC 送内核 → 结果用 LiveKit 数据消息发回（带我们的逐字时间 JSON） | ✅ **推荐作移动端跨网络方案** |
| 直连 WebRTC + OpenAI Realtime 事件 | `webrtc-rs` v0.17（官方注明「生产用这个分支」，tokio 版） | 谷歌 libwebrtc（安卓 / iOS 都有打包好的版本） | 好，但 NAT 穿透和 TURN 要自己配 | 信令（SDP 交换）、数据通道事件、手机端的连接与重连逻辑都要自己写 | 备选：不想多跑 LiveKit 进程时用 |
| Pipecat RTVI 客户端 SDK + SmallWebRTC | 官方服务端是 **Python**，我们是 Rust，只能自己实现 RTVI 协议 | 有 Swift / Kotlin SDK | 官方文档自己写着 SmallWebRTC「适合测试和开发」，生产推荐它家的收费云 Daily | 服务端协议全要自己实现 | ✗ |
| `str0m`（Rust WebRTC） | 只管协议、不带网络线程 | 同 libwebrtc | 同直连 | 同直连，还要自己接网络层 | ✗ 成熟度查不到可靠的生产证据 |
| 纯 WebSocket（`run-task` / OpenAI Realtime） | `tungstenite`（我们已经在用） | 系统自带：安卓 OkHttp、iOS `URLSessionWebSocketTask` | 局域网和好网络够用；弱网一般，靠我们的续传补 | 已在一期里 | ✅ 一期，以及局域网场景 |

**选择 LiveKit 的理由**：跨网络实时语音最难的三件事（NAT 穿透 / 中继、弱网重连、手机端音频采集与编码）它全包了，而且服务端、Rust SDK、手机 SDK 都是同一家开源维护，接口配套。它还正好就是 Gavin 设想的「对外协议服务进程」：LiveKit Server + 我们的识别代理一起当网关。内核和 IPC 一行不变。

**市场检验**（10-17 Gavin 问「有成熟知名软件在用吗」）：
- ChatGPT 高级语音模式：App 里用 LiveKit 客户端 SDK 采音，经 LiveKit 传到 OpenAI 的语音代理（LiveKit 官方博客，2024-10 与 OpenAI 联合发布）。⚠️ 这是厂商自述，OpenAI 没有单独公开架构。
- 公开报道的客户还有 xAI（Grok 语音，2025-12 上特斯拉车机）、Spotify、Salesforce、Meta，以及美国 911 急救接线系统。
- 2026-01 完成 1 亿美元 C 轮，估值 10 亿美元；官方称网络每年承载数十亿次通话。
- ⚠️ **区别要看清**：大客户多数用的是 LiveKit 官方**云服务**。我们用的是**开源版自部署**，核心转发模块是同一份开源代码，但云版另有多地域调度，我们用不上，也不需要（只服务 1~2 路）。自部署的稳定性以我们的 PoC 实测为准。
- Rust SDK 是 LiveKit 的底层核心：官方 Python / Node 代理 SDK 都是通过它的 FFI 层跑的，不是边缘项目。

**代价**（PoC 里核实）：
- 开关打开时多跑一个 LiveKit Server 进程（Go，1~2 路会话负载很轻，PoC 实测内存）；
- 识别代理会带上 libwebrtc，网关程序体积变大，但**主程序不受影响**；
- 许可证要逐个确认，预期是 Apache-2.0；
- Windows 构建要实测。

LiveKit 的转写事件不带逐字时间，所以逐字时间仍走我们的扩展 JSON（§12.4），用 LiveKit 数据消息发回。

**因此原 §6 的「三期自建 QUIC 通道」撤销。** Opus、心跳这些由 WebRTC 自带；断线续传只在 WebSocket 版本保留（服务端缓存，成本低）。

### 14.4 成本对比

| | 自建协议 | 采用开放标准（推荐） |
| --- | --- | --- |
| 要写的东西 | 协议规范、服务端、QUIC 通道、续传、**安卓 SDK、iOS SDK**、文档、测试工具 | 网关里 2~3 个**适配层**：`run-task`、OpenAI Realtime（WebSocket + WebRTC），以后按需加 FunASR |
| 手机 App 开发方 | 只能用我们的 SDK，出了问题只能找我们 | 用阿里示例 / OpenAI 生态 / 任何 WebRTC 库，网上资料多 |
| 弱网质量 | 取决于我们自己在真实弱网里调得怎么样 | WebRTC 十几年的工业积累 |
| 长期维护 | 三端跟着系统升级一起改 | 只维护服务端适配层；标准升级时跟进 |
| 我们仍要自己定义的 | 全部 | 只有扩展字段（`feiyin.*`：逐字时间来源、后处理节点、续传序号），标准客户端会自动忽略 |

### 14.5 怎么做到「多协议但只维护一份逻辑」

网关内部只有**一套事件模型**：开会话 / 音频 / 预览（稳定前缀 + 未稳定尾巴）/ 定稿（文字 + 逐字时间）/ 结束 / 出错。每种协议只是这套模型的「翻译层」，各自几百行，互不影响。内核和 IPC 完全不知道外面是哪种协议。

## 15. PoC 实测结果（2026-10-17，AMD Radeon 780M 集成显卡）

证据：`collab/evidence/491/`（`poc491-concurrency.md` / `poc491-parallel.md` / `poc491-breakdown.md` / `poc491-livekit.md`），测试代码 `src/transcription/poc_asr_server_491.rs`（`#[ignore]`，只测不改生产）。

### 15.1 现状：编排层有并行接口，引擎层串行

- 窗口精解的线程池 + 共享任务队列一直都在（`main.rs:9117` 起），并发度由 `WINDOW_DECODE_CONCURRENCY`（`transcription/mod.rs:2552`）控制。
- 09-23 TUNE-390 实测并发每窗慢 74%、吞吐只 +15%，于是改为 1；换 llama.cpp（DEC-093）时，封装层随之只开一个推理通道（`shim.cpp:207` `n_seq_max = 1`）加一把锁。llama.cpp 库本身支持多通道和批量。

### 15.2 多开推理通道在这块显卡上没用

同一批 17 窗（256.5s 音频），两轮结果一致：1 份引擎串行 29.2s，2 份引擎同时跑 28.2s，**吞吐只提高 4%（1.04 倍），每窗耗时翻倍**（精解中位 1.33s → 2.67s）。显卡已经被一路吃满。

### 15.3 每窗耗时构成（16 窗均值）

| 音频编码 | 提示预填充 | **逐字生成** | 强制对齐 |
| --- | --- | --- | --- |
| 259ms | 102ms | **1004ms（58%）** | 363ms |

逐字生成受内存带宽限制（每个字都要读一遍约 2GB 权重），**只有「批量并行」能给它提速**：多路合成一批，读一遍权重同时出好几路的字。按 3 路估算，总容量最多约 1.6 倍（推算，未实测）。代价是改写封装层的解码调度，并兼容推测解码和前缀复用，风险最高。

### 15.4 本机受影响程度（真实节奏回放，本机 8 窗）

| 场景 | 本机定稿 中位 / 最慢 | 远程定稿 中位 / 最慢 | 本机预览重解中位 |
| --- | --- | --- | --- |
| 本机单独 | 1.8s / 2.4s | — | 65ms |
| + 2 路远程，不设闸门 | 2.5s / 4.9s | 2.1~3.9s / 6.6s | 82ms |
| + 2 路远程，**本机优先闸门** | **2.3s / 3.3s** | 2.4~2.9s / 6.7s | 74ms |

- 预览几乎不受影响。**共用一份预览模型即可**：另开一份 2 线程预览模型反而更慢（远程预览最慢 1.4s），还多占 230MB。
- 本机优先把本机最慢从 4.9s 压到 3.3s。剩下中位 +0.5s 来自「正在解的远程窗不能打断」（每窗约 1.7s）。

### 15.5 结论：三档做法

| 档 | 做法 | 本机影响 | 资源 | 改动 |
| --- | --- | --- | --- | --- |
| A | 排队 + 本机优先（窗口级） | 中位 +0.5s，最慢 +0.9s（实测） | 不增加 | 不改封装层 |
| **B（推荐）** | A + 远程独立推理通道，**逐字生成间隙让路** | 预计只剩编码 / 对齐一段，约 +0.3s（推算，待测） | +约 0.2~0.3GB（一个上下文：KV + 计算缓冲，按 `shim.cpp:203` 注释估） | 封装层**新增**接口，本机路径不变 |
| C | 批量并行 | 远程容量约 1.6 倍（推算） | 少量 | 改解码调度，风险最高；**超过 2 路远程才需要** |

### 15.6 LiveKit（491-P3 / P4 / P5）

- 许可证全部 Apache-2.0。
- Windows 版服务端空载 52MB、空闲不占 CPU；⚠️ Windows 下官方「容量管理」不可用（主力平台是 Linux）。
- Rust SDK 在 Windows 上编译通过，但**必须用静态 C 运行库**（预编译 WebRTC 是 /MT），而主程序按 DEC-085 用动态运行库 ⇒ **LiveKit 只能放在独立网关进程**，再次印证 §2 的 C 方案。
- 识别代理原型（订阅手机音轨 → PCM）全链路跑通：2 部模拟手机同时推，端到端 **64ms**（本机回环），收音无积压无断流；LiveKit Server 约 62MB + 代理 27MB，CPU 合计单核 10% 以内。
- ⚠️ Rust SDK 是 0.x，五周发了 6 个版本：正式接入要锁版本，升级要回归。
- 待测：真实手机 Wi-Fi / 4G 切换（491-P6，需 Gavin 配合）。
