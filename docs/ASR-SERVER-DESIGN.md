# 本地实时识别对外服务 —— 方案（草案，待 Gavin 拍板）

> 单号：`ASR-SERVER-491`（设计阶段，未动代码）　日期：2026-10-17
> 需求原话（Gavin）：「将本地的实时的流式服务扩展成一个本地的流式asr 语音服务，这样可以支持局域网/广域网（通过网络地址）内的其他电脑端的输入法客户端通过 web socket 的协议，或者安卓端/ios 端语音输入法通过协议……来调用」
> 约束原话：「不要在系统的性能、资源占用，还有对现在的架构不会产生破坏性的影响的前提之下，考虑方案」
> 结构建议原话：「把目前的这个本地实时流式的语音服务作为一个核心的服务，另外再增加1层这个服务进程，这个服务专门提供 web socket 和 aoq 的对外的协议连接服务的接口，然后这个服务的进程和我们内核的这个进程之间，通过进程ipc来进行调用」「不会对现有的这个输入法的内核服务产生破坏性的影响。当然，你要仔细考虑是否有更优的方案」
> 启用方式原话：「最终的这个本地流式 asr 语音服务启动的时候，用户可以选择是否启动协议服务进程。如果启动的话，那不光本地语音输入法可以直接用，也可以局网内，或者说外网的其他的电脑终端和 app 端也可以调用」

---

## 0. 结论先说

1. **采用 Gavin 的「内核 + 对外服务进程 + IPC」结构**，只做一处细化：**内核就是现在的输入法进程 `feiyin-ime.exe`**，不另起内核进程。模型只有一份，本机输入法的路径不多一跳。
2. 新增一个独立程序 **`feiyin-asr-gateway.exe`**（下称「网关」），负责所有对外的事：WebSocket、QUIC、鉴权、断线续传、音频解码、并发限流。它**不加载任何模型**。
3. **默认关闭**。关闭时网关不启动、不监听端口、内核里不多占一个线程，行为跟现在逐位相同。
4. **阿里的 AOQ 兼容不了，但可以对标**：AOQ 是阿里私有的 QUIC 传输，只能通过阿里的 Android/iOS/鸿蒙 SDK 连阿里云，没有公开规范。我们在网关里自建 **QUIC 通道**，消息格式跟 WebSocket 版完全相同，能拿到 AOQ 的主要好处：Wi-Fi 和 4G 切换不断线、丢包不卡后续音频、重连快。
5. **对外协议对齐阿里的 DashScope `run-task` 协议**：阿里给输入法推荐的 `qwen-audio-3.1-asr-flash-message` 用的就是它，**我们自己的在线识别客户端也已经在说这套协议**（`src/transcription/qwen_inference.rs:263` `build_run_task_message`）。好处是另一台电脑上的飞音只要把在线识别地址改成局域网地址就能用，客户端几乎不用写新代码。
6. **本机优先**：本机正在说话时，远程会话的精解（1.7B）排队让路。上限是远程最多同时 2 路，超出的连接直接回「忙」。

## 2. 为什么选这个结构（三种做法对比）

| 做法 | 资源 | 对现有架构 | 稳定 / 安全 | 结论 |
| --- | --- | --- | --- | --- |
| A. 服务直接写进输入法进程 | 最省 | 网络依赖进主程序 | 外网来的数据在输入法进程里解析，出问题会**连带输入法崩溃** | ✗ |
| B. 另起一个「内核进程」装模型，输入法也改成通过 IPC 调它 | 模型一份 | **输入法本机路径要整个改造**，多一跳 | 好 | ✗ 破坏面太大 |
| **C. 输入法进程当内核 + 独立网关进程（Gavin 方案）** | 模型一份；网关约十几 MB 内存 | 本机路径不变，内核只多一个 IPC 入口 | 外部数据只在网关里解析；网关崩了自动重启，**输入法不受影响** | ✅ **推荐** |

还考虑过 **D.「内核一行不改」**：远程会话直接排进现在的 worker 线程。代价是 worker 一次只能跑一个会话：远程有人在说话时，本机按热键要么干等，要么把远程掐断，**本机体验反而受损**。所以不选。C 方案对内核唯一的改动见 §4：把本地实时会话那 1700 行**原样搬进独立函数、加参数**，用回放录音保证本机结果逐位不变。这是「内核不被破坏」能做到的最小改动。

C 方案的额外好处：
- 网络相关依赖（QUIC、Opus 解码、TLS 服务端）**只进网关**，主程序体积和依赖不变；
- 网关可以单独重启、单独升级；
- 网关跑在普通用户权限下，攻击面被关在它自己的进程里。

## 3. 整体结构

```
 其他电脑上的飞音 ─┐                       ┌──────────── feiyin-ime.exe（内核，现有进程）────────────┐
 安卓 / iOS 输入法 ─┼─ WebSocket ─┐         │                                                         │
 第三方程序 ───────┘   QUIC ─────┤         │  IPC 服务（新增，一个线程）                              │
                                 ▼         │     │                                                   │
                      feiyin-asr-gateway.exe│     ▼                                                   │
                      · 鉴权 / 限流         │  会话引擎（从 worker 抽出来的本地实时会话，§4）           │
                      · Opus → PCM          │     │  本机录音会话 ──┐                                │
                      · 断线续传缓存        │     │  远程会话 1..2 ─┼─→ 同一份模型（1.7B / 对齐 / 预览）│
                      · 协议翻译            │     ▼                 │                                │
                      · 心跳 / 发现         │  结果 → IPC 回网关     └─ 本机优先调度                   │
                              ▲  命名管道 / Unix socket（仅本机、仅当前用户）                          │
                              └────────────┴─────────────────────────────────────────────────────────┘
```

- **IPC**：Windows 用命名管道 `\\.\pipe\FeiyinIME.AsrCore`，macOS 用 Unix socket，权限只开给当前用户。帧格式是「长度 + 类型 + 内容」，只有 6 种：
  - 网关发给内核：开会话（参数）、音频（16k PCM）、结束、取消
  - 内核发给网关：结果（预览 / 定稿）、出错 / 结束
  - 每路音频 32KB/s，本机管道延迟远低于 1ms，可以忽略。
- **生命周期**：设置里打开开关 ⇒ 内核拉起网关（跟 crash-reporter 同一种拉起方式）。网关意外退出，内核在 5s 后自动重拉。关掉开关或退出输入法，网关一起结束（Windows 用 Job 对象保证不留孤儿进程）。

## 4. 内核里唯一的结构改动：把「本地实时会话」抽成可复用函数

**现状**：会话逻辑内联在 `spawn_worker_thread` 里，而且 worker 线程一次只跑一个会话。如果远程会话也走 worker，本机按热键就要等远程说完，不可接受。

**改法**：把 `main.rs` 约 8940–10700 行原样搬进新模块 `src/transcription/localrt_session.rs`，参数化成：

```rust
pub fn run_session(
    audio_rx: Receiver<Vec<f32>>,   // 本机 = 麦克风；远程 = IPC
    engines: &LocalRtEngines,        // 共享的那一份模型
    opts: SessionOpts,               // 本机 / 远程差异（见下表）
    sink: &mut dyn SessionSink,      // 本机 = 发 PipelineEvent 给浮层；远程 = 发 IPC 帧
    cancel: &AtomicBool,
) -> Result<SessionOutput>
```

- 本机路径：worker 调 `run_session(麦克风, …, 本机选项, 浮层 sink)`，**行为必须逐位不变**。
- 本机与远程的差异只放在 `SessionOpts` 里：

| 项 | 本机 | 远程 | 原因 |
| --- | --- | --- | --- |
| 声纹剔除（DEC-089/099） | 照旧 | **关** | 声纹是本机主人的，远程用户是别人 |
| 近场门 / 跨录音音量沿用（389） | 照旧 | **关** | 按本机麦克风标定，远程设备不适用 |
| 自动学习词库 / 声纹注册 / 使用统计 | 照旧 | **不写** | 远程数据不得污染本机主人的学习数据 |
| 词库注入 | 照旧 | 本机词库 + 客户端 `vocabulary` 追加 | 跟阿里协议的 vocabulary 字段对齐 |
| 预览线程数 | 物理核数（DEC-100） | **2** | 不跟本机抢 CPU |
| 后处理 / 上屏 | 照旧 | 不做 | 见 §5.3 |

- **进程级共享状态要拆成按会话的**：`localrt_vad_session` 的 VAD 缓存（`local_stream.rs:1446`）、`LOCALRT_CARRY_LEVEL` 等现在是进程级单份。远程会话各自建一份 VAD（模型很小）；本机继续用现在的缓存，不变。
- **验收护栏**：抽取前后，用现有回放录音（`replay436_tests.rs` 等）跑本机路径，**事件序列 + 终稿文字逐位相同**。这是「不破坏现有架构」的硬证据。

### 本机优先调度

- 1.7B 精解和对齐的锁外面加一层「本机优先闸」：本机会话在等锁时，远程任务不许插队。
- 远程某一窗已经开始解了，不会被打断。但本机开口后第一次派发至少要等 1.2s 静默或说满 10s（DEC-088），通常那一窗早已解完。**最坏情况本机多等一窗的解码时间，PoC 里实测给出数字**（§7）。
- 本机正在录音时，远程预览的重解间隔从 0.6s 放宽到 1.2s。

## 5. 对外协议

### 5.1 主协议：DashScope `run-task`（WebSocket，PCM 或 Opus 二进制帧）

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| 客户端 → | `run-task` | `parameters.format` = `pcm` / `opus`，`sample_rate` = 16000，可带 `vocabulary`；鉴权放在 `Authorization: Bearer <访问码>` |
| 客户端 → | 二进制音频帧 | 建议 100ms 一帧 |
| 客户端 → | `finish-task` | 说完了 |
| ← 服务端 | `task-started` | 可以开始发音频 |
| ← 服务端 | `result-generated`，`sentence_end=false` | **预览**（SenseVoice 模拟流式），同一 `sentence_id` 会反复更新 |
| ← 服务端 | `result-generated`，`sentence_end=true` | **定稿**（1.7B 精解 + 对齐拼接后），带 `words` 逐字时间 |
| ← 服务端 | `task-finished` / `task-failed` | 结束 / 出错 |

**句子怎么切**：一个派发片对应一个 `sentence_id`。定稿时机就是本机浮层里这段文字「不再被改写」的那一刻（DEC-100 冻结点，加上 DEC-095 对齐晚到后的重拼完成），保证 `sentence_end=true` 之后绝不再改。

**扩展字段**一律放在 `payload.output.feiyin.*` 下，标准客户端会自动忽略：续传序号、本机忙闲提示等。

### 5.2 兼容协议（第二期）：千问实时识别风格

给已经接过 `qwen3-asr-flash-realtime` 的第三方程序用：`session.update` / `input_audio_buffer.append`（base64）/ `session.finish`，回 `conversation.item.input_audio_transcription.text` / `.completed`。在网关里做一层格式翻译，内核不感知。

### 5.3 后处理放在客户端（默认）

服务端只回识别原文，带 1.7B 自带的标点。数字规整、输出优化、翻译、场景格式由客户端自己做，理由：
- 我们的电脑客户端在线识别本来就这么处理，**一行不用改**；
- 输出优化要用的是客户端用户自己的 API Key，场景要看的是客户端那台机器的前台窗口，这些服务端都拿不到；
- 服务端少一份 CPU 负担。

以后手机端如果需要，可以在 `run-task` 里加 `feiyin.postprocess=itn` 让服务端代做数字规整，第一期不做。

## 6. 弱网对策（借鉴 AOQ 的思路，自己实现）

| 手段 | 做在哪 | 效果 | 期数 |
| --- | --- | --- | --- |
| **Opus 压缩** | 客户端编码，网关解码 | 16k PCM 是 256kbps，Opus 语音约 20~24kbps，**流量降到约 1/10**，弱网下不容易堵 | 二 |
| **断线续传** | 网关 | 每帧音频带序号；断线后网关保留会话 15s；客户端带同一 `task_id` 重连时，网关回「已收到第 N 帧」，客户端从 N+1 补发，已发过的结果补推。**会话在内核里不中断**，用户感知只是停顿一下 | 二 |
| **心跳** | 网关 | 跟阿里一样发 `heartbeat=true` / `sentence_id=0` 的保活包，防止路由器 NAT 超时把连接掐掉 | 二 |
| **QUIC 通道（对标 AOQ）** | 网关（Rust `quinn`） | 走 UDP：Wi-Fi 和 4G 切换时连接迁移不断线；丢一个包不卡后面的音频；重连 0-RTT。消息格式跟 WebSocket 版完全相同 | 三 |
| 回声消除 / 降噪 | 手机客户端 | 用系统自带能力（Android `AcousticEchoCanceler` / iOS VoiceProcessingIO），服务端零成本 | 客户端 |

> 关于 QUIC 客户端：iOS 15+ 系统网络库原生支持 QUIC；Android 要带 Cronet 或 quiche 库；浏览器不支持裸 QUIC，所以浏览器场景只用 WebSocket。这也是阿里 AOQ 同样「不支持浏览器」的原因。

## 7. 资源与性能保证（对应 Gavin 的约束）

| 承诺 | 怎么保证 | 怎么验证 |
| --- | --- | --- |
| 关闭时零影响 | 开关关 ⇒ 不拉网关、不建 IPC 线程、不监听端口 | 进程列表 / 端口列表 / 内存对比；本机回放逐位相同 |
| 不多一份模型 | 远程会话共用内核里已加载的那一份；本机档位不是「本地实时」时（模型没加载）服务回「未就绪」，**不为远程单独加载模型** | 开启前后显存 / 内存对比 |
| 本机体验不变差 | 本机优先闸；远程预览 2 线程、本机录音时降频；远程最多 2 路 | **PoC 必测**：本机说话的同时回放 2 路远程录音，测本机每窗精解等待时间和预览刷新间隔，跟单独本机对比 |
| 网关自身 | 不加载模型，预计常驻十几 MB；空闲时不占 CPU | 实测 |
| 不破坏架构 | 本机路径只是「原样搬家 + 加参数」，有逐位护栏 | §4 护栏 |

## 8. 安全与外网

- **只用一个开关**（遵守 DEC-031 单开关原则）：「启动语音识别协议服务（允许其他电脑和手机调用本机识别）」。关闭时只有本机输入法自己用；打开后本机输入法照常直接用（不经网关），同时局域网 / 外网的电脑和 App 可以连进来。打开后自动生成访问码，显示在设置页，可一键复制、可重新生成。端口用固定默认值，不进配置界面。
- 没有访问码一律拒绝；同一 IP 连续输错 5 次锁 10 分钟；音频不落盘。
- **局域网**：第一期就支持。安装包给网关加防火墙规则，**只放行「专用网络」**，公共 Wi-Fi 下不开放。
- **外网**：第一期**不直接暴露公网**，推荐用 Tailscale / ZeroTier 这类组网工具把手机和电脑拉进同一个虚拟局域网，安全和穿透都由它解决。第三期再做内置 TLS 加公网地址，那时需要证书和域名，单独评估。
- 自动发现（第二期）：局域网里用 mDNS 广播 `_feiyin-asr._tcp`，客户端不用手填 IP。
