## 一、R1 · ITN 调用位置回移到 LLM 之前

### 1.1 核心矛盾确认

DEC-035 当初把 ITN 从「LLM 前」移到「LLM 后」，根因是「ASR 把『摄氏』误听成『摄四』→ ITN 字面不匹配 → ℃ 不出现 → LLM 纠正成汉字『摄氏』后再无 ITN 机会」。Gavin 现在要求回移，理由是「LLM 把 `四点三刻` 曲解为 `4:30`，信息被销毁」。

**两个缺陷本质都是「LLM 与 ITN 的先后顺序导致信息丢失」，方向相反**：
- 旧缺陷（已修）：LLM 在 ITN 后，纠正了 ASR 错字但 ITN 拿不到
- 新缺陷：LLM 在 ITN 前，曲解了原始数字表达

### 1.2 主控双通道方案评估

| 维度 | 评估 |
| --- | --- |
| **可行性** | `normalize_unit_symbols` 当前是私有 `fn`（`src/itn.rs:890`，无 `pub`）。独立调用需提升为 `pub fn` 或在 `normalize_numbers` 外新增一个 `pub fn normalize_unit_symbols_only()` 包装。改动面小（1 处可见性 + 1 处调用）。 |
| **幂等性** | **实测验证**（`cargo test --bin feiyin-ime unit_symbol` 11/11 passed，含 `unit_symbol_idempotent`）：主通道产出 `40℃`，补丁通道再跑→`try_match_arabic_symbol` 对 `40℃` 不匹配（`℃` 非 ASCII 数字开头），逐字节抄出。`f(f(x))==f(x)` 成立。 |
| **double-conversion** | 主通道 `normalize_with_rules` 对 `四点三刻`→`4:45`（若 R2 实现）或保持原样（当前）；补丁通道只处理「阿拉伯数字 + 汉字单位」→符号，对 `4:45` 无 trigger，不动。**无撕裂**。反例搜索：唯一风险是主通道产出 `40摄氏度`（若 LLM 把中文数字保留为汉字后补），补丁通道转 `40℃`——这正是预期行为，非 double-conversion。 |
| **三路径覆盖** | 主通道放 `raw_text` 之后天然覆盖三条路径（LLM 成功/失败兜底/关闭）；补丁通道放三分支之后（现 `:3124`）也覆盖三条。**核对 `src/main.rs:2981-3092` 控制流确认无遗漏**：`final_text` 在三分支 `if/else if/else` 之后统一绑定，`normalize_numbers` 在 `:3124` 对所有路径生效。 |

### 1.3 我的关键异议与修正建议

**主控方案成立，但有一处需修正**：

**主控第五点建议「新增 prompt 硬约束」——我认为这条指令已存在，不需要新增，但需要小幅强化。**

`UNIT_SYMBOL_PROTECTION`（`src/llm/mod.rs:29`）已覆盖「成形数字/单位符号原样保留」。当前它列举 `30°C, 50%, 3.5kg, 2026-07-27, 12:30`，已含时间 `12:30`。R1 回移后 `四点三刻`→`4:45` 即被此条保护。

**但存在一个真实缺口**：该指令只说「preserve exactly as written, do not change notation style」，**未明确禁止「时间换算」**。LLM 把 `4:45` 改成 `4:30` 不是「改变记法」，是「改变数值」——属于语义改写，理论上已被 `ANTI_HALLUCINATION`（`do not add information the user did not say`）覆盖，但 Gavin 的实例证明 LLM 仍会犯。

**建议措辞强化**（在 `UNIT_SYMBOL_PROTECTION` 末尾追加一句）：
```
... and do NOT convert symbols to words or words to symbols. You MUST NOT recalculate, round, or re-express any time, date, or numeric value (e.g., 4:45 MUST stay 4:45; do NOT turn it into 4:30 or 16:45).
```

落点：`src/llm/mod.rs:29` 常量字符串追加一句。**零结构改动，零新增指令**。

### 1.4 第六点：`is_effective_text` 门控

`src/main.rs:2927` 当前吃 `raw_text`（DEC-035 第 4 条）。R1 回移后，主通道在 `raw_text` 之后、`is_effective_text` 之前还是之后？

**核对实际代码**：`is_effective_text(&raw_text)` 在 `:2927`，早于 LLM 调用（`:2981`）。若主通道回移到 `raw_text` 之后，应在 `:2927` **之前**还是**之后**？

- ITN 只改数字形态（汉字→阿拉伯 + 符号），不增删语义字符，语气词（啊/呃/嗯）非数字 → filler 判定结果不变。放前放后等价。
- **建议放在 `is_effective_text` 之后**（即 `:2933` 之后），与现有「先判有效再处理」的流程一致，避免对空/filler 文本做无用转换。

### 1.5 R1 最终方案

```
位置1（主通道）：raw_text → is_effective_text 之后、scene 采集之前
  调用：itn::normalize_numbers（完整版 = normalize_with_rules + normalize_unit_symbols）
  职责：四点三刻→4:45（待 R2 实现）、四十摄氏度→40℃

位置2（补丁通道）：三分支 final_text 之后、本地标点之前（即现 :3124）
  调用：itn::normalize_unit_symbols_only（新增 pub 包装，仅第二阶段）
  职责：捞回 LLM 纠正后的 40摄氏度→40℃
```

**影响文件**：
- `src/itn.rs`：`normalize_unit_symbols` 提升 `pub`，新增 `pub fn normalize_unit_symbols_only(text: &str) -> String`（或直接 `pub` 化现有 fn）
- `src/main.rs:2933` 附近：新增主通道调用 `let pre_llm = itn::normalize_numbers(&raw_text)`，LLM 各分支输入改用 `pre_llm`
- `src/main.rs:3124`：`normalize_numbers` 改为 `normalize_unit_symbols_only`
- `src/llm/mod.rs:29`：`UNIT_SYMBOL_PROTECTION` 追加「禁止时间换算」一句

**代价**：LLM 失败兜底路径当前注入 `raw_text`，回移后注入 `normalize_numbers(raw_text)`——这是 DEC-035 之前的行为，Gavin 当时未反对，可接受。但需向 Gavin 说明：LLM 失败时，用户看到的是 ITN 转换后的数字（如 `40摄氏度`→`40℃` 在 LLM 失败兜底也会生效），这是**改进**而非退步。

## 二、R2 · ITN 转换不彻底

### 2.1 缺陷 A：保护词表「撕裂」——主控根因链验证

**我复现确认主控推演逐字正确**：

游标轨迹（`src/itn.rs:690-` 的 `normalize_with_rules`）：
1. `十一` → `check_protection`（`:1082`）命中 `proper_nouns` 的 `"十一"` → 抄出 `十一`，游标 +2
2. `块` → 非数字开头，抄出
3. `九` → `is_unit_preceded`？前文 `十一块` 以 `块`（currency unit，`is_unit` 命中）结尾 → 转 `9`
4. `二` → `consumed==1`，`is_unit_preceded`（前文以 `毛` 结尾）→ 转 `2`
5. 结果 `十一块9毛2` —— **与 Gavin 报告逐字一致**

**这是 `[ITN-PREFIX-SHADOW-001]` 的第三种失败模式：撕裂**。比误保护严重：误保护是整体退回原状（可读），撕裂是同一金额被劈成两半（不伦不类）。

### 2.2 三条修复路径评估

| 路径 | 机制 | 代价 | 反例 |
| --- | --- | --- | --- |
| ① 右邻否决 | 保护命中后检查紧邻右侧是否为单位/量词，是则撤销保护 | `十一月` 的 `月` 是 date_suffix → 误撤销（`十一月`→`11月`） | 需对 `十一月`/`十二指肠` 等追加白名单 |
| ② 语义块锁定 | 保护命中后锁定整个「数字-单位」连续块不转换 | 牺牲转换率换一致性（`十一块九毛二` 全汉字） | `一吨半` 若被锁定则 `半` 也不转，但用户期望 `1.5吨`（见 R2 缺陷C） |
| ③ 块级最长匹配优先 | 先尝试整体识别「数字+单位+数字+单位...」金额块，整体转换，保护词表不参与；整体解析失败才回退逐字扫描+保护 | 改动面最大，最接近「正确」 | `十一国庆` 的 `国庆` 非单位 → 整体解析失败 → 回退逐字 → `十一` 保护命中 → 正确 |

**我的推荐：路径③ 为主 + 路径① 为补丁（而非主控的②兜底）**。

**异议主控的点**：主控倾向「③为主 + ②为兜底」，但我认为②（锁定全汉字）与 Gavin 的总体诉求矛盾——Gavin 要「不能转换得生硬、像机器翻译」，全汉字金额（`十一块九毛二`）在数字密集语境下反而像机器翻译的「未转换」。而①（右邻否决）只在保护词「紧邻单位」时撤销，精确处理撕裂，不影响其他场景。

**③的实现要点**：在 `normalize_with_rules` 主循环开头（`:695` `check_protection` 之前），新增 `try_parse_composite_block`：
- 扫描「中文数字 + 单位 + 中文数字 + 单位 ...」连续块
- 若块内全部可解析（数字串 + 已知单位），整块转换：`十一块九毛二` → `11块9毛2` 或 `11.92元`（按 Gavin 拍板的形态）
- 整体解析失败 → 回退现有逐字逻辑

**待 Gavin 拍板**：金额块的输出形态（见 2.4）

### 2.3 缺陷 B：`半`/`刻` 只识别不转换

`date_specials`（`半`/`刻`）当前只做 `break`（判定「点」非小数点）。要让它产出数值，需新增「余数后缀」文法（见 2.4）。

`四点半` 现状：`四`→`4`（`点`是date_suffix触发），`点半`不在保护表→`半`抄出汉字→`4点半`。**Gavin 报告吻合**。

### 2.4 缺陷 C：余数后缀统一文法

**主控归纳的三型文法我全部确认，并补充歧义裁决算法**：

#### 甲型 · 分数后缀（`N<单位>半` / `N点N刻`）

| 输入 | 语义 | 输出（待定形态） |
| --- | --- | --- |
| 十点半 | 10:30 | `10:30`（规范化）或 `4点半`（口语保形） |
| 五点三刻 | 5:45 | `5:45` |
| 一吨半 | 1.5吨 | `1.5吨` |
| 一个半小时 | 1.5小时 | `1.5小时` |

**算法**：识别 `数字 + 单位 + 半/刻` → `主数 + (0.5 或 0.25)` → 按单位族输出。

**`一个半小时` 特殊处理**：单位是 `小时` 不是 `个`，`一个半` = 1.5。需「量词穿透」规则：`一<量词>半` 中，若量词是通用量词（个/只/条…）且后跟真实单位，则单位=后跟单位。

#### 乙型 · 单位中缀小数（`N<单位>M`）

| 输入 | 语义 | 输出 |
| --- | --- | --- |
| 一米二 | 1.2米 | `1.2米` |
| 三十九度八 | 39.8度 | `39.8度` |
| 五块八 | 5.8元 | `5.8元` 或 `5块8` |
| 一米八五 | 1.85米 | `1.85米` |

**后缀位数决定小数位数**（主控点名要求给规则）：
- `一米二` → `M=二`（1位）→ `1.2`
- `一米八五` → `M=八五`（2位）→ `1.85`
- `三十九度八` → 主数 `三十九`（多位）+ `M=八`（1位）→ `39.8`
- `一百零八度五` → 主数 `一百零八` + `M=五` → `108.5`

**算法**：`parse_cn_number(主数)` + `.` + `parse_cn_number(M)`，M 视为小数部分数字串（非数值，保留位数）。

#### 丙型 · 多级单位链（`N<单位1>M<单位2>K<单位3>`）

| 输入 | 语义 | 输出 |
| --- | --- | --- |
| 十一块九毛二 | 11.92元 | `11.92元` 或 `11块9毛2` |
| 一米八五 | 1.85米 | `1.85米`（同乙型，因米无下级单位） |
| 三小时二十分 | 3:20 | `3:20` 或 `3小时20分` |

**算法**：识别已知单位链（元-角-分 / 小时-分 / 米-厘米 等），按单位进制换算合并。

#### 反例护栏（否决规则，主控点名要求）

`N<单位>M` **不是**小数的情况，必须否决：

| 反例 | 否决理由 |
| --- | --- |
| 三楼二号 | `楼`/`号` 不在「可小数化单位表」（度量衡/货币/时间），属编号 |
| 五排八座 | `排`/`座` 属编号单位 |
| 三年二班 | `年`/`班`——`年`虽是时间但 `班` 非时间下级单位 |
| 第一中学 | 序数语境 |

**否决规则**：维护一个「可小数化单位表」（度量衡：米/度/吨/斤…；货币：元/块/毛/分；时间：点/小时），只有 `单位` 在此表内、且 `M` 是纯数字（无后续单位或后续是同族下级单位）时才合并。其余情况（编号、序数）保持逐字转换或保护。

#### `两` 是否在中文数字表

确认：`parse_cn_number` 支持 `两`=2（`itn-rules.toml` 数字表含 `两`）。`两点半`→`2:30` 正常。

| 万 | 万宁、万里长城（已入表）、万州、万年、万荣 |

**预估规模**：去重后约 60-80 条（≥3 字），2 字词约 20 条（高风险，单独评估）。

### 3.4 2 字词风险单独说明

2 字词遮蔽面最大（`十堰` 遮蔽 `十堰的`、`三亚` 遮蔽 `三亚市`）。**建议本次只加 ≥3 字专名，2 字词维持现状**（`三亚`/`九江`/`四川` 等已入表的保留，新增 2 字词逐条评估）。

### 3.5 反向护栏脚本设计（不实现）

```
对每个候选词 W：
  生成测试串 = W + 每个单位字（块/度/米/吨/点/分...）
  断言 normalize_numbers(W + 单位) 不会因 W 保护而撕裂后续
  例：十三陵 + "块钱" → "十三陵块钱"（无意义但不应撕裂）
       十三 + "块钱" → 应转 "13块钱"（若十三不在保护表）
```

实际执行时需 R2 缺陷 A 修复后验证：若路径③块级匹配优先，则 `十三陵` 保护命中后，`十三陵块钱` 整体解析失败→回退逐字→`十三陵`保护+`块钱`转`13`？不，`十三陵`保护抄出后游标到`块钱`，`块`非数字，`钱`非数字，不转换。安全。

### 3.6 分桶与性能

现有 `unit_collision_map` 是 `HashMap<char, Vec<String>>` 分桶（`src/itn.rs:1114`）。R3 新词应**复用 `protect.proper_nouns` 分组**（人工维护），而非并入 `unit_collisions`（机器派生）。理由：
- `proper_nouns` 优先级高于 `unit_collisions`（`check_protection` 顺序，`:1092` 在 `:1113` 之前）
- 地名属人工精选，不应与机器派生词表混用
- 性能：`proper_nouns` 当前是 `HashSet` 线性遍历（`:1093`），新词增加遍历成本，但 60-80 条增量可忽略

## 四、R4 · 格式化输出的列表智能

### 4.1 场景覆盖（实读 `scene-rules.toml` 给事实）

| 场景 | multiline_safe | 列表是否放开 |
| --- | --- | --- |
| 聊天/IM（微信/钉钉/QQ/飞书…） | false | ❌ 压平 |
| AI Agent（豆包/Kimi/ChatGLM…） | false | ❌ 压平 |
| 邮件客户端（Outlook/Foxmail/Thunderbird） | true | ✅ 放开 |
| IDE/编辑器/终端 | false | ❌ 压平 |
| 文档/笔记（Word/Notion/Obsidian…） | true | ✅ 放开 |
| 浏览器（通用） | false | ❌ 压平（靠 title 细分邮箱/文档） |

**结论**：列表只在 `multiline_safe=true` 场景（邮件、文档/笔记）放开。聊天框/终端/浏览器（含搜索框）压平。

### 4.2 压平时的降级形态

`multiline_safe=false` 时，现有 F3 指令（`src/llm/mod.rs:837`）已是：「join items inline with appropriate separators (e.g., commas)」。即 `1. xxx；2. yyy` 或 `xxx, yyy, zzz`。

**我的建议**：降级形态用「`1. xxx；2. yyy`」（带序号内联），而非纯逗号。理由：有序枚举的序号语义在压平后仍需保留（「第一/第二」对应的内容不可丢失次序标记）。现有指令已足够，无需改动。

### 4.3 纯文本符号选择（主控点名问题）

注入目标多为微信/Word/记事本等**非 Markdown 渲染环境**，`- ` 或 `1. ` 原样显示字面符号。

| 符号 | 可读性 | 推荐场景 |
| --- | --- | --- |
| `1. 2. 3.` | 高（通用书写） | 有序列表，所有场景 |
| `• ` | 中（项目符号，记事本可能显示为 `?` 或乱码 depending on encoding） | 无序列表，邮件/Word（非纯文本记事本） |
| `- ` | 中（Markdown 环境」会渲染，纯文本原样显示） | 不推荐，混用易乱 |
| `① ② ③` | 中（带圈数字，优雅但输入法难输入，LLM 可能误用） | 不推荐 |

**我的推荐**：
- 有序列表：`1. 2. 3.`（最通用，记事本/Word/邮件全兼容）
- 无序列表：`• `（项目符号），但**降级到纯文本环境时**用 `- ` 或直接段落（因 `•` 在 GBK 记事本可能乱码）

**关键约束**：LLM 在 `multiline_safe=false` 时不应输出 `• `（会被压平成 `• xxx；• yyy`，可读性差）。`• ` 只在 `multiline_safe=true` 且非纯记事本场景用。鉴于场景判定已由 `scene-rules.toml` 完成，可在 F3 指令中按 `multiline_safe` 参数化符号选择。

### 4.4 判据设计：LLM 判定 vs 规则前置

**我同意主控倾向：由 LLM 在 F3 指令内判定，不在 Rust 侧规则前置。**

理由：
1. 枚举意图识别是语义任务，「首先/然后」vs「有的/有的」的边界模糊，规则表覆盖不全且易误触（如「然后我们就走吧」中的「然后」是时间连接非枚举）。
2. LLM 天然擅长语义判定，且现有 F3 指令（`:814`）已列举触发词（第一/第二/首先/其次/最后）。
3. 风险：LLM 过度格式化（把普通两句话硬拆成列表）。需**保守默认**。

**建议 F3 指令强化**（`src/llm/mod.rs:814` multiline_safe=true 分支追加）：
```
...only restructure surface form.
Only use a list when the speech EXPLICITLY contains enumeration markers (第一/第二, 首先/其次/最后, 一是/二是, 第1点, one/two/three). If unsure, DO NOT use a list — keep the text as a continuous paragraph. Over-formatting normal speech into lists is a regression.
```

**few-shot 示例**（追加到 F3 段末）：
```
Examples:
- "第一点xxx，第二点yyy" → "1. xxx\n2. yyy"
- "首先xxx，然后yyy，最后zzz" → "1. xxx\n2. yyy\n3. zzz"
- "有的xxx，有的yyy" → "• xxx\n• yyy"
- "今天天气不错我们去公园吧" → "今天天气不错我们去公园吧" (NO list)
```

- `src/llm/mod.rs:837`（multiline_safe=false F3 指令）：已足够，可选强化降级形态为带序号内联
