**任务**：RESEARCH-ASR-057 | **负责人**：coder-1 | **性质**：纯研究，零代码改动 | **完成时间**：2026-08-19

## 一、来源

Gavin 要求和主控**同时独立研究**在线 ASR「按下热键→首字上屏」的提速方案，之后两份对照取优。基线在 `target/release/debug.log`（Gavin 08-18 真实端测）。主控已拆出 09:41:13 那次：热键 13.564 → 录音 13.569 → VAD 命中 14.508（938ms）→ 连接完成 14.617（108ms）→ 首个非空文本 15.096，合计 ≈1.53s。

## 二、复核主控判断：938ms 是「人的反应时间」而非程序延迟

**✅ 同意主控判断。**

从 debug.log 提取全部 6 次录音的 VAD 命中延迟：

| 会话 | 热键时间 | VAD 命中 | VAD 延迟 |
|------|---------|---------|---------|
| S1 (09:32:53) | 53.423 | 54.115 | 692ms |
| S2 (09:40:18) | 18.322 | 20.254 | 1932ms |
| S3 (09:40:49) | 49.678 | 49.696 | **18ms** |
| S4 (09:41:13) | 13.564 | 14.508 | **944ms** |
| S5 (09:45:06) | 06.794 | 07.573 | 779ms |
| S6 (09:45:27) | 27.781 | 28.505 | 724ms |

**证据**：
- S3 = 18ms，证明 VAD 本身几乎零延迟——Gavin 几乎在按下热键的同时就开始说话

- 6 次延迟范围 18-1932ms，差异完全来自 Gavin 何时开口
- **程序侧无可控优化空间——不能替用户决定何时说话**

## 四、六个研究点逐条结论

### ① 热键按下即建连、VAD 命中即发音频（收益约 108ms）

**当前串行**：VAD 命中 → DNS+TCP+TLS+WS 握手（108ms）→ task-started → 发 pre-roll → 发实时 chunk

**提议并行**：热键按下即建连 → VAD 命中时连接已就绪 → 立即发 pre-roll + 实时 chunk

| 项 | 内容 |
|----|------|
| 收益 | **108ms**（实测稳定，6 次 108-117ms）|
| 风险 | 低。① 若 VAD 2s 保底未命中也要建连（已有逻辑）；② 连接建立后不发音频服务端可能超时——需确认 task-started 后多久不发音频会断开 |
| 红线 | 不是 040-C 跨请求连接池，无空闲连接被杀问题（每次新连接，用完即关）|
| 证据 | debug.log 6 次连接耗时 108-117ms 稳定 |
| 结论 | **✅ 值得做**。收益 108ms（实测稳定），风险可控。需确认服务端 task-started 后不发音频的超时阈值 |

### ② task-started 往返实测多久、能否与 pre-roll 准备重叠

| 项 | 内容 |
|----|------|
| 实测 | task-started 往返 35-39ms（均值 36ms）|
| 当前 | 收到 task-started 后才发 pre-roll（串行）|
| 提议 | 发 run-task 后立即开始准备 pre-roll PCM 编码（与等 task-started 重叠）|
| 收益 | **35ms**（task-started 往返时间）|
| 风险 | 极低——pre-roll 编码是纯 CPU 操作，与网络等待天然可并行 |
| 结论 | **✅ 可做但收益小（35ms）**。实现简单（提前编码 pre-roll PCM bytes）|

### ③ pre-roll 600ms 是否可只灌 VAD 命中点往前 N ms

| 项 | 内容 |
|----|------|
| 实测 pre-roll 时长 | S1=1.3s / S2=2.5s / S3=0.3s / S4=1.5s / S5=1.4s / S6=1.3s |
| 分析 | pre-roll 包含热键按下到 VAD 命中的全部音频。VAD 命中点之前的静音段不含语音，可裁剪。但 VAD 检测有延迟（能量门限滞后），实际语音起点可能在 VAD 命中点之前 100-300ms |
| 收益 | **≈0ms**。pre-roll 上传是 16kHz×2bytes = 32KB/s，1.3s = 41KB，以网络带宽论上传 <10ms。减 pre-roll 对延迟几乎无影响 |
| 风险 | **🔴 高**。FIRSTCHAR 修复历史漫长（D1-D3+FIX-005），减 pre-roll 可能复现送气清声母丢失 |
| 结论 | **🔴 拿不准维持现状**。减 pre-roll 收益≈0，风险高 |

### ④ 上传分片 100ms 改小能否让服务端更早解码

| 项 | 内容 |
|----|------|
| 当前 | AUDIO_CHUNK_BYTES=3200 = 100ms @ 16kHz/16bit/mono |
| 分析 | 分片越小服务端越早拿到数据开始解码，但太小会增加 WS 帧开销。官方示例统一用 3200 bytes（100ms），未找到其他推荐值文档 |
| 收益 | **不明**。服务端首字延迟（均值 283ms）与分片大小关系不明确——首字延迟主要来自服务端模型推理时间 |
| 风险 | 中。改小可能增加 WS 协议开销（每帧有 2-14 字节头部）|
| 结论 | **❌ 查不到可靠依据维持现状**。100ms 是官方示例值 |

### ⑤ 服务端首字约 400ms，fun-asr 是否更快

| 项 | 内容 |
|----|------|
| 实测 qwen 首字延迟 | 199-440ms，均值 283ms（6 次）|
| fun-asr 是否更快 | Gavin 研究发现 fun-asr-realtime 比当前模型快（ASR-056 任务书已述）。但「快」指首字还是最终结果未明确 |
| 协议文档 | 两模型共用同一 Inference API，首个 partial 时机由服务端模型推理速度决定 |
| semantic_punctuation_enabled=false | 不增加首个 partial 延迟（标点是后处理）|
| multi_threshold_mode_enabled | 查不到可靠依据，保持默认 |
| 结论 | **✅ fun-asr-realtime 已在 ASR-056 集成，A/B 对比可端测验证首字延迟差异** |

### ⑥ 上屏侧：tween_audio_origin + SetTimer + InvalidateRect

| 项 | 内容 |
|----|------|
| tween_audio_origin | 首个非空文本到达时置位。首字立即显示（words 空→立即全显降级；words 非空→按 begin_time 揭示）|
| SetTimer 重绘周期 | overlay 用 16ms timer（~60fps），首字到达后最多多 1 帧 = 16ms 延迟 |
| StreamingText→InvalidateRect | main.rs 收到 StreamingText → OverlayCommand::Show → overlay 线程 InvalidateRect(hwnd, None, false) → WM_PAINT 重绘。无可省的中间跳转 |
| 收益 | **≤16ms**（1 帧 timer）|
| 结论 | **❌ 无可优化空间** |

## 五、第 7 点：停顿压缩分析（Gavin 追加）

### 背景

Gavin 要求重新评估 DEC-054「不压缩停顿」红线。技术上已取回 end_time 字段但没用上，可算词间空档 `gap = begin[i] - end[i-1]`，把超过阈值的 gap 钳到上限。

### 主控推演验证

主控推演：收益在「backlog 补发时」（服务端一次性下发覆盖数秒的词表，文字其实已经全知道了，却按原速滴出来，包含中间的死时间）。而用户真的在停顿时，服务端本来也没有新词可给。

### S4 真实数据分析

用 S4（主控拆解那次）的 25 条 result 序列做分析：

**result 到达间隔分布**：
- 24 个间隔全部在 907-1463ms 范围
- **0 个间隔 > 1500ms**（无真正的停顿死时间）
- 间隔均值 ~1100ms，这是服务端的固定出字节奏（每约 1s 吐一批）

**关键发现**：
1. result 到达间隔基本均匀在 1000-1400ms——这是服务端的固定出字节奏，不是「停顿」
2. 服务端在持续处理音频，没有「死时间」可压缩
3. **words[].begin_time/end_time 具体值未在日志中打印**（只打 words 数量），无法精确计算 gap

### 收益分析

**🔴 查不到 words[].begin_time/end_time 的具体值，无法精确计算收益。**

但从 result 间隔分析可以推断：
- 如果每批 2-6 字的 begin_time 跨越 ~1s（与 result 间隔一致），则按 begin_time 揭示 ≈ 按 result 到达节奏揭示，**停顿压缩收益 ≈ 0**
- 如果每批 2-6 字的 begin_time 跨越 < 1s（用户说得快，服务端处理慢），则存在 backlog 补发场景，**停顿压缩有收益**

### 结论

**🔴 建议：在 debug.log 增加 words[].begin_time/end_time 的详细日志，Gavin 再录一次 -debug，用真实 words 时间戳数据做精确计算。拿不到数据时不要硬做——DEC-054「不把节奏做假」是明确红线。**

### 阈值建议（若数据显示有收益）

如果 words 数据显示 backlog 补发场景确实存在：
- `gap = begin[i] - end[i-1]`
- 阈值 = **300ms**（句内停顿 100-300ms 不压缩；句间停顿 > 300ms 压缩到 300ms 上限）
- 依据：语音学常识，句内停顿 100-300ms，句间停顿 300-2000ms
- 风险：压缩句间停顿会破坏 DEC-054「不把节奏做假」，但 Gavin 明确要求重新评估
- **🔴 但这个阈值只有在确认 backlog 补发场景存在后才有意义。没有数据，不实施。**

## 七、最优组合建议

**组合 ①+②**：热键即建连 + task-started 与 pre-roll 编码重叠 = 节省 **~143ms**

- 这 143ms 在 S4（主控拆解那次）中占总延迟 1532ms 的 **9.3%**，体感明显
- VAD 延迟（938ms）是人的反应时间，不可控；143ms 是程序侧唯一可省的
- 实现风险低，不碰 FIRSTCHAR / DEC-054 红线

**建议不做的项**：
- ③减 pre-roll：收益≈0 风险高
- ④分片改小：查不到依据
- ⑥上屏侧：无空间
- ⑦停顿压缩：需要 words 时间戳数据才能判断，当前日志不含此数据
